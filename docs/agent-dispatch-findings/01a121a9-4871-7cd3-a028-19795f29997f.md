# Unified dispatch design and validation

## 2026-10-09 — Standalone routing logic

The user clarified that the dispatcher is a unified entry point. Destination
conversations answer directly, without result aggregation or reporting obligations.
Jev may choose reuse or creation; uncertain cases reach the dispatcher LLM. The
user authorized implementing the logic and tuning against existing threads, with
no messages to those threads and permission to create Luna/low test conversations.

Implemented separate read-only inventory capture, bounded candidate retrieval,
Jev Choice decisions, delivery eligibility, and a local routing history that
deduplicates plans and supplies deferred LLM catch-up. Recent planned assignments
inform later routing immediately, including a destination still being created.
There is no app interception, message sender, provider wake, or creation executor
in the new logic or evaluator.

Validation used a frozen snapshot of 213 existing conversations plus two new
`gpt-6-luna` / `low` fixtures: vendor form
`01a12252-c8e0-7e62-84fe-06cc54f5ade7` and Helm chart
`01a12252-ccf1-77b3-931c-360f1894da8e`. The delivery audit found only creation
messages 4040 and 4041 from this work, both to those fixtures; no messages went
to pre-existing threads. Fixtures discussed hypothetical designs and made no
implementation changes.

Compared five Jev configurations on 24 hand-authored development cases. The
eight-candidate continuity policy matched 22/24 expectations on its selection
run, versus 16/24 for a simpler prompt, 18/24 with four candidates, and 20/24
with twelve candidates. Both the pinned model and preview alias returned
`jev-1.13.0`; their differences cannot establish a model capability difference.
Kept confidence >= 0.75, winning probability >= 0.70, and margin >= 0.20;
lowering the confidence floor to 0.65 did not improve the selected run.

After freezing the selection, all 20 held-out expectations matched: 15 automatic
routes and five dispatcher fallbacks, with no incorrect automatic assignments.
All 13 expected reuse destinations appeared in the shortlist. Median decision
latency was 0.605 seconds and p95 was 0.674 seconds on the local snapshot,
excluding live inventory capture and provider startup/task execution.

A repeated development run matched 20/24, with 15 automatic routes rather than
17. The additional fallbacks were confidence variation near the cutoff; neither
run made an incorrect automatic assignment. This small single-user benchmark
is not a production accuracy estimate. Cases are newly authored against current
history, not historical replays; age, file changes, and some execution states
are explicitly labelled counterfactual overlays. No confidence threshold was
tuned on the held-out cases.

Final validation ran 754 Python tests successfully (one optional skip), including

## 2026-10-09 — Opt-in app integration

Implemented a persistent **Use as dispatcher** setting, available in conversation
actions and the overview menu. The composer routes requests asynchronously and
provides **Ask dispatcher directly**. Requests and destination receipts appear in
the dispatcher timeline; destination conversations receive ordinary user input
and answer directly. Dispatcher input continues to route while its LLM is busy.

`dispatch_runtime.py` persists ordered intake, classifier evidence/latency,
creation identity, queued delivery, provider acceptance, and uncertain outcomes.
It reuses the normal message queue, rechecks execution guards, and never blindly
retries uncertain creates or sends. Existing settings survive reuse; newly
created conversations initially use the dispatcher's provider/model/effort with
normal permissions. Creation defaults are persisted independently. Turning off
dispatcher mode cancels intake that has not begun; accepted queue entries retain
their normal queue controls.

Before a dispatcher provider invocation, bounded catch-up supplies prior original
requests and current delivery states. Only provider acceptance advances its
cursor. `agent-coord thread dispatch-history --session-id <id> --after <cursor>`
pages full saved request text and routing events. Existing actionable LLM
assignments also inform subsequent Jev retrieval through the coordination store.

Live provider validation exposed a retrieval bug: hooks can normalize
`sessions.cwd` to a repository root while the app conversation uses a nested
working directory. Candidate snapshots now use `browser_sessions.cwd`, with a
compatibility fallback for older inventories. A regression test covers this.
An earlier ACK-only fixture produced a conservative Jev fallback; the selected
confidence gates were retained. The final fixture had actual retained design
context and exercised ordinary requests as well as an explicit thread mention.

Final validation: 777 Python tests passed with one optional skip, including
48 routing/integration tests; all 413 JavaScript tests passed. Both installed
plugins match 105 source files. Five live checks using Jev and `gpt-6-luna` at
low reasoning completed successfully: reuse, explicit continuation, creation,
reuse of the created thread, and direct dispatcher fallback. The fallback
correctly described the vendor and crossword destinations from catch-up history.
Retries retained the original request identity. Live tests used isolated stores;
the production-store audit found no outgoing messages from this implementation
thread during integration work. No existing user conversation was used as a
test destination.

The desktop and phone-width UI checks verified designation, receipts, direct
fallback, and destination navigation, using an isolated simulated provider.
The rebuilt local app is `build/dispatch-integration/Ribbon Field.app`; its 87
backend/assets files match source and its signature verifies. Focused native
files/UI smoke passed and all owned native test backends exited. Full native
smoke fails at `roll_up_oldest_waiting` in both this build and the installed
baseline; that pre-existing Roll up limitation remains outside this change.
