## 2026-10-08 — Actionable routing reopens closed specialists

Message 3821 explicitly revises the earlier preserve-Closed decision: ordinary
actionable routing should return a closed app specialist to Now, with the same
agent tooling interface. Implemented in `agent-coord-c0j`; the shared experiment
journal is intentionally unchanged.

`CoordinationStore._insert_message` moves only a closed app recipient to Now
within the message transaction. This covers a running specialist consuming the
request immediately through a hook, an idle specialist, and offline app routing.
It retains the thread ID, title, original request, history, associations, model,
effort, and permissions. Informational/closure messages and terminal recipients
do not reopen; Now/Later placement and snoozes are otherwise untouched. Delivery,
acknowledgement, and wake retries do not repeat the placement mutation. Fresh
`send`/`reply` calls remain new messages under the existing CLI semantics.

UI placement is now independent of provider archival throughout the affected
runtime paths. `BrowserSessions.__init__` migrates provider archival into placement
only for legacy conversations lacking a work-thread row, so restart cannot undo
a persisted reopen. `list_sessions` filters by UI placement. `send` restores the
provider for accepted direct input as well as eligible automatic wake; an older
request queued before Close also reopens when dispatched. Settings controls and
`BrowserMessageQueue._open` use placement, allowing settings changes and explicit
user queue resumption in a reopened but still provider-archived conversation.

The inbox worker's durable claim, Stop, failed-turn, uncertain-submission,
pending-Close, and queued-user-input gates are unchanged. Making a conversation
visible does not authorize execution through these gates. A stopped thread can
therefore appear in Now while waiting for direct user continuation. Close does
not suppress messages; a pending close still controls execution. Provider
unarchive/resume stays behind the automatic claim and eligibility checks.

No frontend change is required: the existing message insertion trigger feeds
`message_timeline.message_changes`, and the UI's SSE handler schedules overview
refresh. The selected conversation and tiled panes also refresh metadata on the
existing five-second timer; normal dispatched turns publish `browser/changed`.
HTTP validation checks the reopened thread in the open inventory, absent from
Closed, with a usable direct message route while provider wake remains paused.

README and coordination guidance now describe the revised behavior. The CLI
syntax and managed terminal `delegate` behavior are unchanged. Native deployment
and app restart are excluded from this assignment; unlike the earlier hook-only
instruction change, these runtime changes need an updated app backend for full
activation.
